# Documentation maintenance, style as code and measurement

## Content aging
- Every page has an **owner** and a last review date (in the file header, e.g. `owner`, `last_reviewed`).
  Pages older than an agreed period (e.g. 6 months for guides, every release for reference) go
  to review — a list generated by a script in CI.
- A behaviour change in code = a documentation change in the same PR (SKILL.md); a PR template with the field "documentation
  updated / not applicable".
- Link checking (internal and external) and code example checking in CI; a dead link or an outdated example is
  a bug like any other.
- Outdated pages: you update them, redirect them or mark them as archived with a link to the new version —
  you do not leave them without a comment.

## Where to get topics and gaps
- **Support tickets and chats**: recurring questions (category, count) → missing or unclear pages.
  Every ticket resolved with a link to the documentation is proof the page works; resolved without a link — a candidate
  for new content.
- **Documentation search**: queries with no results and with results but no click.
- **Communities** (forums, Stack Overflow, Reddit, repository issues): how people name the problem — use these words
  in titles.
- **Talking to experts and testing the product yourself** (the process in `process.md`); the source code as the final source
  of truth about behaviour.

## Style guide and linting
- A short team style guide in the repo (`docs/STYLE.md`): tone, form of address, preferred and banned terms
  (the domain glossary — ddd-facilitation), formatting (headings, lists, code blocks), how to write numbers, dates and units.
  Base it on existing ones (Google Developer Documentation Style Guide, Microsoft Writing Style Guide) — in matters
  that are not specific to the Polish language.
- **Vale** — a style linter in CI: `.vale.ini` with `StylesPath`, `MinAlertLevel`, ready packages (`Packages = Google`,
  fetched by `vale sync`) and the project's own vocabulary (a list of accepted and rejected terms). The ready
  packages are for English; for Polish texts your own rules (terms, banned words) and
  `txt-polish-correctness/scripts/polish_lint.py`.
- The `error` level blocks a PR only for certain rules (a banned term, a wrong product name); the rest as suggestions,
  so that the linter does not put people off.

## Measurement
- Task metrics matter more than page views: whether the reader reached the goal (moving to the next step, a quick start
  run, a drop in tickets on a topic), a page rating ("was this helpful?" with a comment field).
- Documentation analytics compliant with GDPR (consent, no personal data in events — proc-product-discovery).
- A quarterly review: the most visited pages with a low rating → fixes; pages without traffic → merge or remove.
