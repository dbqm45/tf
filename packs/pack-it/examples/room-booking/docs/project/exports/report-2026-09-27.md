## Phase summaries

### Brief: Room and desk booking  ·  _accepted_

A company (300 people, a hybrid work model) books rooms and desks in a spreadsheet — double bookings happen. Goal: a web application
for self-service bookings with an integration with the Microsoft 365 calendar. Success: 90% of bookings self-service within 3 months,
zero double bookings. Constraints: MVP in 3 months, a team of 2 × TypeScript/Angular + 1 × Java, Azure hosting in the EU.

### Requirements: Room and desk booking  ·  _accepted_

6 MVP stories. Key attributes: no double bookings under concurrency, M365 SSO, 99.5% availability during working hours.

### Stack decision: Room and desk booking (MVP)  ·  _accepted_

A modular monolith: **Java 25 + Spring Boot 4.1 + Spring Modulith 2.x** (back end) and **Angular 22 + MSAL Angular** (front end, served by the same application), database **Azure Database for PostgreSQL Flexible Server 18**, hosting **Azure App Service (Linux)** in one EU region, M365 integration through **Microsoft Graph** (outbox, one-way synchronisation).
Why: (1) the database guarantees the "0 double bookings" scenario — an **exclusion constraint** on (resource, time slot), regardless of the code; (2) a stack the team knows (TS/Angular + Java/Spring), with the fewest parts to maintain; (3) a new resource type = data + a policy in the Resources module, without changes to the booking schema.
The biggest risks: the source of truth for rooms, if the rooms are already resource mailboxes in Exchange (a question for IT), Graph permissions (the M365 administrator's consent), the availability of the services in the Poland Central region, one Java developer. We check them with spikes S0–S4 in the first 2 weeks.
Note: no domain phase (02-domain) — the "Availability" model is adopted as a **[proposal]** based on stories H1–H4.

### Delivery plan: Room and desk booking (MVP)  ·  _proposed_

8 steps (vertical slices), each deployable. Step #1 (skeleton + CI) right after this plan is accepted.
The first slice with business value: #2 (H6 SSO) → #3 (H1 room booking, without M365). The M365 integration (#8) is
moved to the end and depends on IT's answer (S2/S3) — without it H1 works, only without an entry in the M365 calendar.
Bottleneck: 1 Java developer for the whole `booking`/`resources`/`identity` module — the back-end steps go sequentially.
