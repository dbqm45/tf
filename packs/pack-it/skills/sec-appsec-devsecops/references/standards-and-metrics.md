# AppSec standards and metrics

## ASVS
- Version 5.0.0 released 30.05.2025 (secondary source: the OWASP Global AppSec EU 2025 announcement and a reference table; 17.10.2026).
  The first major release in about five years; the numbering of requirements and chapters differs from 4.0.3, so mapping
  old references (e.g. V2 → the new chapter) requires the table from the OWASP document [unverified: exact chapter breakdown].
- Three levels: L1 (the baseline for every application), L2 (most applications with sensitive data), L3 (critical).
  A requirement has an identifier; in the backlog cite the identifier, in a test state which item it proves.
- Use: not "compliance with the whole ASVS", but choosing the chapters relevant to the application and acceptance tests from them.

## SAMM
OWASP SAMM (Software Assurance Maturity Model) assesses an organization's program in business functions (among others governance,
design, implementation, verification, operations) on a maturity scale of 1–3 [unverified: the current version,
I assume 2.x]. Apply it every year: assessment, 2–3 goals per quarter, reassessment.

## NIST SSDF (SP 800-218)
- **Version:** SSDF 1.1 (SP 800-218, final, 03.02.2022) is the applicable basis. SSDF 1.2 (SP 800-218 Rev. 1) is
  a draft for consultation from 17.12.2025 — do not cite it as a final version. The profile for AI models:
  SP 800-218A (final, 26.07.2024).
- **Four practice groups:** PO (prepare the organization: roles, requirements, tools, criteria), PS (protect the software:
  the repository, release integrity, the archive), PW (produce well-secured software: design and threat model, review
  and tests, secure defaults, dependencies), RV (respond to vulnerabilities: intake of reports, root cause
  analysis, remediation).
- **Use without paperwork:** SSDF says "what", not "how". Make a table practice → a control you already have (a scanner,
  a PR gate, an SBOM, a signature, a reporting process) → evidence from the system (a CI log, a report, a register entry) → gap. The evidence
  is an artifact generated by the pipeline, not a document written for the audit. A customer asking about compliance gets this
  table with links to the evidence.
- Mapping onto this skill: PW ↔ control layers and code review; PS ↔ the artifact supply chain (SLSA, signatures);
  RV ↔ triage and SLA (`triage-and-sla.md`); PO ↔ requirements (ASVS) and people (security champions).

## OWASP DSOMM
The OWASP DevSecOps Maturity Model assesses the maturity of security practices **in the pipeline** (build, deployment,
tests, culture, information), in levels from basic to advanced, with concrete activities at each
level [unverified: the current version — the project does not publish numbered releases in the sources found].
SAMM answers the question "how mature is the organization's security program", DSOMM — "what else
to automate in the team's pipeline". Use DSOMM to choose the next 2–3 steps, not to assess the team.

## Shift left and secure defaults
- **Shift left** = a control at the earliest point where it can be done cheaply and with a good signal: the requirement
  and the threat model before the code, a scanner in the IDE and in the PR, not only a pentest before release. It does not mean shifting
  all responsibility onto developers without tools and support.
- **Secure defaults** (secure by default): a new service, template or module starts with
  authentication, TLS, minimal permissions enabled and debug mode disabled; disabling a safeguard requires
  an explicit decision. Templates and golden paths: ops-platform-engineering.

## Metrics (formulas)
- **Vulnerability MTTR** = the mean (or the median, more robust to outliers) time from detection to closure, separately per severity.
- **Overdue** = open past the SLA / open in total.
- **Coverage** = repositories with each layer / active repositories (separately SAST, SCA, secrets).
- **Precision** = true / examined in a sample; measure per rule.
- **Escapes** = vulnerabilities found after deployment (pentest, report, incident), with an attribution of which layer
  should have caught them.
