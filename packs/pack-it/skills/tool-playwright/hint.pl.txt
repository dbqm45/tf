# Playwright — testy e2e i API

Wersje: napisane dla 1.63, działa od 1.44; przed użyciem nowszego API sprawdź tabelę niżej. Dowody: `skill.meta.json`.

## Zasady
1. **Oczekiwane wartości pochodzą z przypadku testowego albo kryterium akceptacji**, nigdy z tego, co aplikacja pokazuje dziś
   (qa-spec-first-testing). Nazwa testu niesie id: `test('TC-014: suma zamówienia z dostawą', …)`.
2. **Lokatory w tej kolejności:** `getByRole(rola, { name })` → `getByLabel` → `getByText` → `getByTestId`. CSS i XPath na końcu.
   Jeśli elementu nie da się znaleźć po roli i dostępnej nazwie, to zwykle **problem z dostępnością** — opisz go zamiast
   sięgać po selektor CSS.
3. **Asercje web-first** (`await expect(locator).toHaveText(…)`, `toBeVisible`, `toHaveURL`) same czekają i ponawiają.
   Nigdy `page.waitForTimeout()` ani stałych uśpień.
4. **Izolacja:** każdy test dostaje świeży kontekst przeglądarki. Stan przygotuj przez API albo plik `storageState` tworzony
   w projekcie setup — nie klikaniem przez UI i nie licząc na to, że inny test uruchomił się wcześniej.
5. **Czas i sieć:** czas kontroluj przez `page.clock` (`setFixedTime`, `install` + `runFor`) — 1.45+. **Zewnętrzne** usługi mockuj
   przez `page.route()` albo plik HAR (`routeFromHAR`); własne API zostaw prawdziwe.
6. **Mało testów e2e,** tylko dla krytycznych ścieżek użytkownika. Reguły i obliczenia testuje się niżej (qa-test-design §4).
7. **Znany defekt:** `test.fail(true, 'BUG-231 zaokrąglanie ceny')` albo `test.fixme()` z linkiem do błędu. Nigdy nie zmieniaj
   oczekiwanej wartości, żeby test przeszedł.
8. **Testy API** używają fixture `request` (`request.post('/api/orders', { data })`) — bez przeglądarki.
9. **Fixture zamiast page objectów** dla wspólnego przygotowania; page object jest w porządku dla długich przepływów, ale asercje zostają w teście.

## playwright.config.ts dla CI
```ts
import { defineConfig, devices } from '@playwright/test';
const CI = !!process.env.CI;
export default defineConfig({
  testDir: 'e2e',
  fullyParallel: true,
  forbidOnly: CI,                       // zapomniany test.only wywala build
  retries: CI ? 2 : 0,                  // wykrywacz niestabilności, nie przykrywka
  failOnFlakyTests: CI,                 // 1.52+: przeszedł przy ponowieniu = przebieg nieudany
  reporter: CI ? [['blob'], ['github']] : 'html',
  use: { baseURL: 'http://localhost:3000', trace: 'on-first-retry' },
  webServer: { command: 'npm run start', url: 'http://localhost:3000', reuseExistingServer: !CI },
  projects: [
    { name: 'setup', testMatch: /.*\.setup\.ts/ },
    { name: 'chromium', use: { ...devices['Desktop Chrome'], storageState: 'e2e/.auth/user.json' }, dependencies: ['setup'] },
  ],
});
```
- Niestabilny test to błąd w teście albo aplikacji: otwórz trace (`npx playwright show-trace`), napraw przyczynę, nie zwiększaj ponowień.
- **Zestawy po tagu:** `test('TC-020: termin dostawy', { tag: '@smoke' }, …)`, uruchamiane przez `npx playwright test --grep @smoke`.
- **Tylko to, czego dotknął PR:** `npx playwright test --only-changed=origin/main` (1.46+). Na starszych wersjach: uruchom tag `@smoke`
  plus pliki spec zmienione w diffie (`git diff --name-only origin/main -- e2e`).
- **Sharding:** `--shard=1/4` na zadanie CI, raporty blob, potem `npx playwright merge-reports --reporter html ./all-blob-reports`.

## Dostępność
- `await expect(page.getByRole('main')).toMatchAriaSnapshot(…)` (1.49+) sprawdza drzewo dostępności; snapshoty przeglądaj jak kod.
- Automatyczny skan: `@axe-core/playwright` (`new AxeBuilder({ page }).analyze()`) plus ręczne przejście klawiaturą.
- `page.accessibility` usunięto w 1.57 — używaj aria snapshotów albo axe.

## Wbudowani agenci testów (1.56+)
`npx playwright init-agents --loop=claude` (albo `vscode`, `opencode`) dodaje **plannera** (bada aplikację, pisze plan),
**generatora** (zamienia plan w testy) i **healera** (naprawia padające testy). Ich wynik traktuj jak pull request juniora.
Healer może poprawiać **lokatory i oczekiwania czasowe**; nigdy nie może zmienić oczekiwanej wartości ani sprawdzanego tekstu — zmienione
oczekiwanie to sprawa dla właściciela wymagania, nie naprawa.

## Generowanie E2E przez agenta AI
Zanim poprosisz agenta o testy: wzorcowy spec (`tests/e2e/seed.spec.ts`), spisane konwencje, zlecenie zadania, eksploracja
przez `playwright-cli`, przegląd antywzorców, sprzątanie danych (afterEach, projekt teardown) i weryfikacja przez celowe zepsucie kodu: `references/e2e-with-agent.md`.

## Przykład
„Test przycisku Przelicz jest niestabilny i używa klasy CSS”:

```ts
test('TC-031: przeliczenie liczy dostawę', { tag: '@smoke' }, async ({ page }) => {
  await page.clock.setFixedTime(new Date('2026-03-02T10:00:00'));   // cennik dostawy zależy od daty
  await page.goto('/cart');
  await page.getByLabel('Ilość').fill('10');
  await page.getByRole('button', { name: 'Przelicz' }).click();     // było: page.locator('.btn-recalc')
  await expect(page.getByRole('status')).toHaveText('Dostawa: 0,00'); // H4-AC1: darmowa od 100,00
});
```
Jeśli `getByRole('button', { name: 'Przelicz' })` nic nie znajduje, bo „przycisk” to `<div>` z obsługą kliknięcia,
potraktuj to jako problem z dostępnością.
