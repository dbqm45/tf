# Debugowanie — od objawu do przyczyny, potem poprawka, która nie maskuje

Najpierw przyczyna, potem poprawka. Pracuj pętlą eksperymentów: obserwuj → postaw hipotezę → przewiduj → sprawdź → wnioskuj. Prowadź
krótki dziennik tego, co sprawdzono i co wyszło — chroni przed powtarzaniem i pozwala przekazać pracę.

## Procedura
1. **Opisz objaw.** Oczekiwane a faktyczne; od kiedy; gdzie (środowisko, wersja, commit, dane, użytkownik); pełny komunikat i stack trace,
   nie streszczenie. Różnica środowisk („u mnie działa”) to pierwszy podejrzany. Zgłoszenie w jednym zdaniu bez stosu („nie działa”) →
   najpierw pytania do zgłaszającego: kroki, kogo dotyczy, jak często, który obszar. Nie zgaduj przyczyny.
2. **Odtwórz.** Najmniejszy powtarzalny przypadek, najlepiej automatyczny test **czerwony z właściwego powodu** — to pierwszy krok TDD
   poprawki (`tdd_guard`). Błąd losowy: pętla N uruchomień; przypnij ziarno, zegar, kolejność testów i równoległość. Brak odtworzenia →
   raport „nie udało się odtworzyć” z listą prób; nigdy nie ogłaszaj poprawki.
3. **Hipotezy.** 2–4 kandydatki; dla każdej: co musi być prawdą i który eksperyment rozstrzyga. Najpierw najtańszy rozstrzygający, nie
   ulubiony. Jedna rzecz naraz.
4. **Zawężaj** (przykłady: `references/bisection-and-tools.md`):
   - **historia** — `git bisect run <skrypt>`: kod 0 = dobry, 1–127 poza 125 = zły, 125 = nie da się sprawdzić (pomiń), powyżej 127
     przerywa. Około log2(n) kroków (200 commitów ≈ 8). Skrypt poza repozytorium albo nieśledzony; czysty build i cache między krokami;
     dużo merge'y → `git bisect start --first-parent`; monorepo → ograniczenie ścieżką; najpierw sprawdź, że koniec „zły” jest czerwony,
     a „dobry” zielony; zapisz `git bisect log`; zakończ `git bisect reset`. Pominięty commit obok pierwszego złego daje uczciwą odpowiedź
     z dwoma kandydatami;
   - **dane** — dziel wejście na pół do najmniejszego przypadku (delta debugging); trafia do testu regresyjnego bez danych osobowych;
   - **kod** — logi i asercje na granicach modułów, z kontekstem (identyfikatory, wartości wejścia);
   - **środowisko** — różnice wersji z lockfile, zmienne, flagi, dane, system.
5. **Obserwuj.** Debugger (`breakpoint()`, `python -m pdb`, `pytest --pdb`; `node --inspect-brk` + `chrome://inspect`, `debugger;`).
   Idź wstecz od awarii: awaria ← zainfekowany stan ← defekt.
6. **Sprawdź założenia.** Czy uruchamiasz ten kod, co myślisz (stary build, nieaktualny bajtkod `__pycache__`, cache, serwer bez
   przeładowania, zła gałąź)? Wersje zależności, konfiguracja? Strefy czasowe, kodowanie, locale?
7. **Przyczyna źródłowa.** Pytaj „dlaczego” aż do defektu i luki: czemu wartość była zła, czemu to przeszło, czemu testy tego nie złapały.
8. **Poprawka bez maskowania.** Czerwony → minimalna poprawka → zielony → cały zestaw. Zakazane maski: pusty `except`/`catch`, ślepy
   retry, `sleep` w testach, wyłączenie testu albo reguły lintera. Poszukaj kopii tego samego wzorca (`rg`).
9. **Zapisz.** W raporcie kroku: objaw, przyczyna, dowód, poprawka. Pułapka, która może wrócić → `docs/project/lessons.md`.

## Klasy przyczyn — pierwszy eksperyment
Niedeterminizm (pętla, przypięte ziarno i zegar); stan współdzielony — przechodzi sam, pada w zestawie (przetasuj kolejność, szukaj
globali); wartości brzegowe (dziel wejście); czas i strefy (wstrzyknięty zegar, inny `TZ`); cache i artefakty (czysty build,
`PYTHONDONTWRITEBYTECODE=1`); środowisko (różnice wersji, zmiennych); zależność (bisekcja zmiany lockfile); współbieżność (test wielowątkowy,
logi z request id); połknięty błąd — 200 / `ok: true` bez skutku (test sprawdza zapisany stan w bazie, nie odpowiedź;
`references/evidence-from-many-sources.md`: monitoring, logi, przeglądarka, poprawka w dwóch częściach).

## Kiedy przestać i zmienić podejście
- Brak postępu po długiej sesji albo wszystkie hipotezy obalone → przekaż dziennik człowiekowi lub agentowi ze świeżym kontekstem
  (limit rzędu dwóch godzin to heurystyka zespołu [założenie]).
- Wpływ na produkcję → najpierw przywróć usługę (ops-sre-incidents).
- Druga nieudana poprawka tego samego objawu, plan, który się nie zbiega, albo zgłoszenie łączące objaw, przyczynę i poprawkę („duplikaty —
  dodajmy blokadę”) → przeramowanie problemu: `references/reframing.md` (obserwacja, założona przyczyna, kierunek; hipotezy z dowodami
  plik:linia; `frame.md`).
- Hook `tdd_guard` pokazuje ten sam padający test po 1–2 próbach → przestań łatać, procedura od kroku 1.

## Przykład
Raport faktur liczył dobrze dwa tygodnie temu, ~200 commitów później źle. Czerwony test `test_march_totals` (HEAD czerwony, tag sprzed
dwóch tygodni zielony); skrypt poza repo z `git clean -fdx`, kod 125 przy nieudanym buildzie; `git bisect start --first-parent`,
`git bisect run` → 8 kroków → commit „float sum in aggregation”. Przyczyna: float zamiast `Decimal`; poprawka plus test właściwości;
`rg` znalazł drugą kopię.
