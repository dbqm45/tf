# Factory versioning and releases

The factory has one version number following [Semantic Versioning 2.0.0](https://semver.org/) (`MAJOR.MINOR.PATCH`)
in the file `core/factory/VERSION`. A released version is marked by the git tag `vX.Y.Z` (e.g. `v2.7.0`), and every tag
gets a GitHub Release with the entry from `core/factory/CHANGELOG.md`. The highest tag is the default source for
`tf update` (`factory/update.py`) from a git repository (`<repo>#vX.Y.Z` pins the version).
What belongs to the public API (and so affects the kind of bump) is described in [core/factory/PUBLIC_API.md](../core/factory/PUBLIC_API.md).

## Commits: Conventional Commits

Commits and **PR titles** use the [Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) format.
PRs are merged with *squash merge*, so the PR title becomes the commit on `main` and decides the next version.
The description from the title goes straight into the CHANGELOG, so it is written in English (like PR titles).

```
<type>(<scope>)!: <description>

[body: why, not what]

[footers, e.g. Refs: #21  or  BREAKING CHANGE: <what and how to migrate>]
```

- **Description**: in English, imperative mood (`add`, `fix`, not `added`), no trailing period, max 72 characters (the ` (#NN)` suffix from squash merge does not count).
- **Scope** (optional), lowercase, e.g. `install`, `update`, `build`, `hooks`, `skills`, `release`, `deps`.

| Type | When | Effect on version |
|---|---|---|
| `feat` | new feature (skill, persona, facet, flag, command) | MINOR |
| `fix` | bug fix | PATCH |
| `perf` | faster, no behavior change | PATCH |
| `refactor`, `test`, `docs`, `style`, `build`, `ci`, `chore`, `revert` | no change in behavior for the user | none |
| `!` after the type/scope or a `BREAKING CHANGE:` footer | backward-incompatible change (any type) | MAJOR |

Examples:

```
feat(skills): add eng-repo-readiness skill with a repo readiness audit
fix(hooks): detect git -C outside the project in guard_bash
feat(install)!: write --shared workflows to .github instead of .claude
docs: describe the release process
chore(release): 2.7.0
```

Checking:

- **CI**: the `pr-title` workflow (`.github/workflows/pr-title.yml`) rejects a PR title that does not match the format.
  It also runs after a title edit.
- **Locally** (optional, once per clone): `git config core.hooksPath .githooks` enables the `commit-msg` hook.
  You can check a single message with `python3 scripts/check_commit_message.py "feat(install): …"`.
- Messages generated by git (`Merge …`, `Revert "…"`, `fixup!`, `squash!`, `amend!`) are not checked.

## Which bump (SemVer)

The **most serious** change since the last tag decides.

| Change in the public API | From 1.0.0 | In the 0.y.z phase |
|---|---|---|
| backward-incompatible (`BREAKING CHANGE:` footer or `!`) | MAJOR | MINOR |
| backward-compatible new feature (`feat`) | MINOR | PATCH |
| fix (`fix`, `perf`) | PATCH | PATCH |
| documentation, tests, CI, refactoring only | no release | no release |

The factory is already past 1.0.0, so the left column applies. The computation (including the 0.y.z phase) is done by
`core/skills/core-semver/scripts/semver.py`; the release scripts only use it.

## How the version is bumped (automatically)

After every merge to `main`, the `release` workflow (`.github/workflows/release.yml`) does the following in order:

1. **Computes the version** (`python3 scripts/release.py --ci`): takes the commits since the last `vX.Y.Z` tag and
   applies the tables above.
   - No `feat`, `fix`, `perf` and no incompatible changes means no new version: the run ends with no changes.
   - Otherwise the script writes the new version to `core/factory/VERSION` and adds an entry at the top of
     `core/factory/CHANGELOG.md` (sections *Breaking*, *Added*, *Fixed* from the commit titles; English names as in [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), older entries have Polish names and stay unchanged). The sections match
     the `build.py check` validation (kind of bump ↔ sections), which the job runs before committing.
   - On a MAJOR release (`X.0.0`) the script raises the upper bound `requires.core: "… <X.0.0"` to `<X+1.0.0` in
     `packs/*/pack.yaml` and `modes/*/pack.yaml`; otherwise `build.py check` would reject every overlay with the new
     core. An overlay that really does not work with the new core must have a different bound in the same PR.
2. **Commits** these changes to `main` as `github-actions[bot]` with the message `chore(release): X.Y.Z`. A push with
   the `GITHUB_TOKEN` token does not trigger further workflows, so the release commit does not trigger the next release.
3. **Creates the tag** `vX.Y.Z`, annotated, on the release commit.
4. **Creates the GitHub Release** `vX.Y.Z` with the CHANGELOG entry as its body (`python3 scripts/release_notes.py X.Y.Z`).
   An existing Release is left unchanged. A missing one (e.g. the run failed after the tag was created) is created by
   the next run on `main` or a manual workflow run (*Run workflow*).

Several PRs merged in quick succession: the runs wait in a queue (`concurrency: release`), so they will not compute the
same version twice. If a new commit lands on `main` during a release, the push of the release commit is rejected, and
all the changes are released by the run started for the newer commit.

In an ordinary PR you **do not change** `core/factory/VERSION` or the CHANGELOG headings; CI does that.

### When to release manually

A manual PR is needed only when the result computed from commits has to be overridden: a commit was labeled wrongly,
you want to rewrite the CHANGELOG (e.g. add a *Deprecated* section), or you are deliberately releasing a MAJOR.

1. On a fresh branch from `main` run `python3 scripts/release.py --dry-run`, then
   `python3 scripts/release.py minor` (or `major` / `patch` / `X.Y.Z`).
2. Review and rewrite `core/factory/CHANGELOG.md`, then `python3 tools/workspace.py check`.
3. Make a `chore(release): X.Y.Z` commit and open a PR with the same title.
4. After the merge, the workflow notices an untagged version in `core/factory/VERSION` and releases it without
   recomputing: it checks for the `## [X.Y.Z]` entry in the CHANGELOG (without it nothing is tagged), and then proceeds
   as in steps 3-4 above.

Rules:

- **A released version is never changed.** We do not move or delete a tag. A mistake in a release is fixed by the next
  version.
- **Deprecation**: first a MINOR with a *Deprecated* section and an alias, removal only in the next MAJOR
  (core/factory/PUBLIC_API.md).

## GitHub repository settings

- *Settings → General → Pull Requests*: **squash merge** enabled (PR title as the commit message).
- *Settings → Actions → General → Workflow permissions*: the `release` workflow needs `contents: write` (it declares it
  itself); the `main` protection rule must allow `github-actions[bot]` to push the release commit.

## Dependency updates (Dependabot)

`.github/dependabot.yml` opens one PR a week with new versions of GitHub Actions. Its title has the form
`ci(deps): bump …`, so it passes the `pr-title` check, and after merging it does not bump the factory version (type `ci`).
