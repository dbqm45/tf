The tf factory · as of 16 November 2026

Map of the tf factory

The factory installs a team of AI agents for Claude Code in your project. The agents come with ready knowledge, fixed rules and guards that make sure the rules are not broken. This page shows what the factory is made of, what you can adjust in it and how the work flows. Some things already work, some are planned.

factory core, working add-on bricks, working planned, not there yet guards (enforce the rules)

The whole on one picture

On the left, the settings stacked in floors. In the middle, the agents you work with and the bricks that add knowledge to them. On the right, the path of a task from ticket to pull request. At the bottom, the guards that enforce the rules at every step. The following sections describe each part in detail.

Structure: the foundation and the settings floors

The factory is easiest to imagine as a building. The core is the foundation, the same for everyone. Each floor above adjusts the factory for a narrower group: the whole company, one team, one project and finally you. A floor can add something of its own or tighten the rules, but it cannot break them. If the company has banned something, no team or developer can unblock it.

narrowest scope · decides last
Youworking

Your way of working: whether the agent acts on its own, asks for consent at every step, or just talks. Plus the default task mode and your shortcuts. It applies to all your projects and does not go into the repository.

tf style · ~/.tf/preferences.yaml · .tf/config/me.yaml (this project only)
also: CLAUDE.local.md, .claude/settings.local.json, working and commit language
Projectworking

Settings of one repository: own personas, roles and skills, limits for unattended work, and the overlays and modes chosen for this project.

.tf/config/config.yaml · .tf/config/personas/ · .claude/skills/
Teamworking

Standards and settings shared by the repositories of one team, above the company standards: its own code rules, ticket prefixes, tools. A team can only tighten the company's bans and narrow the allowed work modes.

overlay pack-<company>-<team> · generator: org/new_org_pack.py <company> --team <team>
Companyworking

Standards of the whole organization: what the agent must not do (e.g. publish), what always goes to human review, automatically checked code rules, Jira and ticket prefixes, a cost profile.

overlay pack-<company> from the company's own repository · generator org/new_org_pack.py
Coreworking

The foundation: the engine that builds the agents, installs and updates the factory, runs the work loop /tf-task, counts costs and keeps the project journal. Plus 22 skills with work rules and the guards (hooks) that work regardless of the model's decisions.

.tf/factory/ · .claude/hooks/ · .claude/skills/core-*
common to everyone

Bricks: what you add to the foundation

On every floor you can add ready-made bricks. An overlay brings knowledge of one domain together with personas, that is agents with a specific specialization. A mode changes the way of working and is switched on only when needed. Bricks are added with tf add and removed with tf remove.

How work on a task goes

You type /tf-task and a ticket number (or several). The factory takes the task from the ticket to a finished pull request. /tf is work with the factory without the loop, /tf-design a design session before any code. Each step is done by an agent matched to the task, the cheapest one that can handle it. Underneath, the guards work all the time.

You choose the mode for each task: tf task mode <KEY> plan|normal|auto. Alongside the loop there are also tools with no model and no cost: tf analyze (review of the project and company standards) and tf risk (change risk assessment).

Your work style working

Every developer works differently. A style is a ready set of settings on the "You" floor that sets several switches at once: tf style autonomous, tf style step-by-step albo tf style conversation. A single task can still get a different mode. The style works within the limits set by the company and project.

autonomous

"Let it run by itself, show me the result."

  • Auto mode by default, if the company allows it
  • a question pauses only the slice of work that depends on it
  • a report at the end, cost limits apply

step-by-step

"I want to see and approve every step."

  • normal mode: code only after the plan is approved
  • a stop after every slice of work
  • the plan and changes to review before the next step

conversation

"I prefer to talk and decide what next myself."

  • the task ends at the plan
  • code only when you change the task mode
  • then approval after every slice of work
  • Claude Code in planning mode: even an ordinary conversation does not change files without approval

You install the factory privately (nothing goes into the repository, everyone installs it themselves) or as a team (--shared, the factory is committed together with the project). Addresses and tokens, e.g. for Jira, never live in overlays, only in environment variables.
