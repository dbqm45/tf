# Numery wersji — sklasyfikuj zmianę, policz skryptem

Numer wersji to obietnica zgodności **względem zadeklarowanego publicznego API**. Klasyfikujesz, co zmieniło się
w tym API, bierzesz najpoważniejszą zmianę i liczysz numer skryptem — nigdy z pamięci.

Skrypt (uruchamiasz, nie czytasz): `python3 .claude/skills/core-semver/scripts/semver.py`
- `valid` — kod 0 poprawna, 1 niepoprawna z powodem;
- `compare A B`, `sort V…` — pierwszeństwo, metadane builda pomijane;
- `bump 2.4.1 major|minor|patch` → 3.0.0 / 2.5.0 / 2.4.2; `bump 1.2.3 pre --id rc` → 1.2.4-rc.1, kolejne `pre` → rc.2, `release` usuwa sufiks;
- `next [--since vX.Y.Z] [--path P] [--current V]` — podbicie z commitów od ostatniego tagu: `!` lub `BREAKING CHANGE` → major,
  `feat` → minor, `fix`/`perf` → patch; w fazie 0.y.z zmiana niezgodna → minor, reszta → patch; brak tagu → kod 2, podaj `--current`;
- `check-changelog CHANGELOG.md [--version-file VERSION] [--strict-from V]` — nagłówki `## [X.Y.Z]` od najnowszego, bez powtórzeń,
  najnowszy = plik wersji; od `--strict-from` sekcje pasują do podbicia (Niezgodne/Usunięte → major, Nowe/Wycofywane → co najmniej minor).

## Procedura
1. **Publiczne API zapisane** w README albo `PUBLIC_API.md`. Bez spisu numer nic nie znaczy — najpierw spisz API.
   Co jest API dla danego typu produktu: `references/public-api.md`.
2. **Ostatnia wydana wersja:** najnowszy tag `vX.Y.Z`, plik wersji, górny wpis changelogu. Rozjazd — najpierw uzgodnij.
3. **Czy artefakt się zmienił?** Typ commita opisuje intencję i może się mylić; zawartość paczki nie kłamie. Porównaj pliki,
   które trafiają do paczki od tagu: `git diff --name-only v1.4.0..HEAD -- src/ package.json` albo `npm pack --dry-run`.
   - nic z wydawanych plików się nie zmieniło → **bez wydania**, nawet przy `feat:` (tylko CI, testy, dokumentacja);
   - pliki paczki się zmieniły, a są tylko commity `chore:`/`docs:` → ostrzeż człowieka.
4. **Sklasyfikuj każdą zmianę** i weź najpoważniejszą. Niezgodna wstecz = istniejące poprawne użycie przestaje działać
   albo po cichu działa inaczej bez zmiany po stronie użytkownika.
5. **Policz** `bump` (i porównaj z `next`); wygrywa wyższe, różnicę wyjaśnij.
6. **Zaktualizuj razem** pliki wersji, changelog (nowy wpis na górze), instrukcje instalacji; uruchom `check-changelog --version-file`.
7. **Tag** `vX.Y.Z` (tag ma `v`, wersja nie), push i publikacja — **tylko po zgodzie człowieka**. Nie przesuwasz tagów,
   nie publikujesz ponownie istniejącego numeru.

## Którą część podbić
- niezgodna wstecz (usunięcie, zmiana nazwy, nowe wymagane wejście, ostrzejsza walidacja, inny typ błędu, usunięcie przestarzałego) → **major**;
- nowa zgodna funkcja (nowy eksport, opcjonalny parametr, nowy endpoint lub pole) oraz **oznaczenie czegoś jako przestarzałe** → **minor**;
- zgodna poprawka błędu, łatka bezpieczeństwa, aktualizacja zależności bez zmiany API → **patch**;
- refaktor, testy, CI, dokumentacja bez zmiany zachowania → bez wydania.
- **Wycofywanie:** oznaczasz w minor (ostrzeżenie, zamiennik, dokumentacja), trzymasz co najmniej przez jedno minor,
  usuwasz w kolejnym major.
- **Poprawka, na której ktoś polega:** oceniasz względem zadeklarowanego API, nie intencji.
- **Błędne wydanie:** nie przepisujesz go; wydajesz nową wersję przywracającą zgodność i zapisujesz w changelogu, która była wadliwa.

## Faza 0.y.z i 1.0.0
- Nowy projekt startuje od **0.1.0**; przy major 0 API może się zmieniać w każdej chwili.
- Konwencja fabryki w 0.y.z: niezgodna → minor, reszta → patch.
- **1.0.0**, gdy działa na produkcji, ktoś na nim polega albo dbasz już o zgodność wstecz. Decyduje człowiek; ty proponujesz.

## Wersje przedpremierowe i metadane
- `2.0.0-beta.1` jest **niżej** niż `2.0.0`. Identyfikatory od lewej: liczby liczbowo, tekst w kolejności ASCII, liczba niżej
  niż tekst, dłuższa lista wygrywa przy równych początkach: `alpha.beta` < `beta.2` < `beta.11` < `rc.1` < wydanie.
- Licznik zawsze po kropce: `rc.9` < `rc.10`, a `rc10` sortuje się przed `rc9` (porównanie tekstu).
- Metadane builda po `+` są pomijane w kolejności; nie rozróżniają wydań.

## Przypadki brzegowe
- Monorepo: każdy pakiet ma własną wersję. Wersja w URL (`/v1`) to osobna decyzja (be-api-design).
- Obraz: pełny tag niezmienny, tagi `1`, `1.4`, `latest` tylko do przodu w obrębie zgodności.
- Zależności projektu: core-stack-sync. Format commitów: core-conventional-commits.

## Przykład
Biblioteka 2.4.1: dodany opcjonalny parametr i usunięta funkcja oznaczona wcześniej jako przestarzała.
Opcjonalny parametr → minor, usunięcie → major; wygrywa major: `bump 2.4.1 major` → **3.0.0** (nie 2.5.0 — oznaczenie było w minor).
Changelog `## [3.0.0]` z sekcjami Usunięte i Nowe, plik VERSION = 3.0.0, `check-changelog` przechodzi, tag po zgodzie człowieka.
