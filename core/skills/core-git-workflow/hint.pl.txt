# Przepływ pracy z git — gałęzie, commity, PR, przegląd, scalanie

Format komunikatu commita należy do core-conventional-commits; ten skill obejmuje wszystko wokół niego.

## Nigdy bez wyraźnej zgody człowieka
`git push --force` (także `--force-with-lease`), `git reset --hard`, `git clean -fd`, przepisywanie wypchniętej historii,
push na `main`/`master`. Najpierw zapytaj, powiedz, co przepadnie, zaproponuj bezpieczną alternatywę.
- Rozjechana własna gałąź po rebase → `git push --force-with-lease` na *twojej własnej* gałęzi feature, po zgodzie.
  Odmówi, jeśli ktoś w międzyczasie coś wypchnął. Nigdy force na `main`/`master` ani na wspólną gałąź.

## Gałęzie
- Utwórz gałąź przed pierwszą edycją; nigdy nie commituj prosto na `main`/`master`.
- Nazwa: `<typ>/<krótki-opis>`, np. `fix/login-timeout`. Praca z kluczem zmiany niesie go małymi literami:
  `story/tsk-57-csv-export`, a każdy commit na niej ma stopkę `Change: TSK-57` — hook commit-msg z
  core-conventional-commits odrzuca commit bez niej na takiej gałęzi. Klucz pochodzi z planu zmiany albo od człowieka;
  nigdy go nie wymyślasz.
- Gałęzie krótkie, częsta integracja (trunk-based; szczegóły w eng-continuous-delivery, pack-it).

## Commity
1. `git status`, potem przejrzyj, co wchodzi: `git diff`, a po dodaniu `git diff --staged`.
2. Dodawaj pliki po ścieżce. `git add -A` / `git add .` tylko po przeczytaniu całego diffu.
3. Nic, czego nie należy wersjonować: `.env`, klucze i tokeny (sekrety), zrzuty, wyniki budowania, duże binaria.
4. Testy i lint przechodzą przed commitem.
5. Jedna logiczna zmiana na commit; komunikat według core-conventional-commits. Zły komunikat: amend tylko ostatniego
   commita, tylko niewypchniętego, tylko na prośbę.
- Poprawka po przeglądzie lub przeróbka ma `Rework-Cause:` z `spec-gap`, `agent-error`, `requirement-change` albo `unknown`.
  Wybierz prawdziwą przyczynę; `unknown` nie jest domyślne. `tf metrics` je liczy.

**Commit na fazę planu** (konwencja fabryki):
- Dodaj tylko pliki zmienione w tej fazie i jej raport kroku. Inne zmienione pliki → pokaż je i zapytaj: tylko ta faza
  (zalecane) / wszystko / przerwij. Przed pierwszym commitem zmiany sprawdź indeks, czy ktoś wcześniej czegoś nie dodał.
- `git diff --cached --quiet` kończy się kodem 0 → nic do commita; nie rób pustego commita.
- Temat `<typ>(<id-zmiany>): <tytuł fazy> (f<N>)`, pliki w treści. `Refs:` tylko z odnośnikami od człowieka albo z rozmowy —
  nigdy z nazwy gałęzi.
- Hook odrzuca commit → usuń przyczynę i zrób nowy commit. Bez `--no-verify`, bez `--amend` (przepisałby commit poprzedniej fazy).
- Po commicie wpisz jego SHA w listę Postęp raportu kroku (core-project-record); SHA ostatniej fazy i końcowy status
  raportu idą w osobnym commicie zamykającym.

## Praca równoległa
Zacznij od dwóch zmian naraz — limitem jest to, ile człowiek nadąży przejrzeć, nie ile agentów da się uruchomić.
1. **Sprawdzenie niezależności:** wspólne pliki, kontrakty API/typów/schematu, migracje, usługi zewnętrzne. Konflikt →
   jedna po drugiej.
2. **Jedna zmiana = jeden worktree + gałąź + świeża sesja:**
   `git worktree add ../<repo>-<zmiana> -b feat/<zmiana>`. Główny katalog tylko koordynuje. Po scaleniu
   `git worktree remove`; pozostałości: `git worktree list`, `git worktree prune`.
3. **Worktree izoluje pliki i gałąź, nie środowisko.** Każdy dostaje własny port serwera dev, lokalną bazę danych
   lub schemat (migracje!), sandbox kolejki/płatności, cache. Świeży worktree nie ma `node_modules` ani `.env`. Operacje git
   na wspólnym repozytorium mogą zderzyć się na `.git/index.lock`. Tej samej gałęzi nie da się mieć w dwóch worktree.
   Zużycie dysku rośnie z zależnościami.
4. **Zmiana kontraktu w trakcie:** od razu napisz do drugiej sesji w tej postaci:
   „Zmiana kontraktu: <co> w <plik/commit>. Wymagane: <działanie>. Odpowiedz «przyjęte».” Druga strona nie scala, dopóki
   nie odpowiedziała „przyjęte”. Kanały: `SendMessage` do nazwanej sesji, `/peers` do listy, `@nazwa-sesji` w poleceniu;
   bez nich wiadomość przekazuje człowiek. `claude agents` grupuje sesje czekające na ciebie pod „Needs input”.
5. Wybierz tryb: decyzje po drodze → interaktywnie, faza po fazie; zamknięty zakres z mierzalnym końcem → `/goal` z limitem
   tur (core-delivery-lifecycle). Każda zmiana ma własny przegląd i własny PR; poboczne usprawnienia stają się nowymi
   pozycjami planu. Koszt równoległych sesji: `.claude/skills/core-cost-control/references/parallelism.md`.
Szczegóły i lista kontrolna sesji: `references/parallel-worktrees.md`.

## Pull requesty
- Tytuł jak temat commita. Treść: Co (1–3 punkty), Dlaczego, Jak przetestowano, Ryzyka i wycofanie; link do planu lub
  wymagań w `docs/project/`.
- Małe: jedna zmiana, kilkaset linii. Większe dziel.
- **PR-y pisane przez agenta — agent proponuje, potok decyduje:**
  - oznacz je: etykieta (np. `agent`) i trailer commita (`Co-Authored-By:`), żeby historia pokazywała, co napisał agent;
  - chronione ścieżki (`infra/`, auth, płatności, `.github/workflows/`, `.claude/`) mają właścicieli w CODEOWNERS i są
    wyłączone z auto-merge; zielony przebieg nic nie dowodzi, gdy PR zmienia workflow, który go wygenerował; `tf risk`
    ocenia te ścieżki wysoko;
  - zakres zostaje przy zadaniu, zmiany spoza zakresu są cofane (agent `scope-reviewer`);
  - infrastruktura pisana przez AI dostaje więcej bramek, nie mniej. Uprawnienia agentów w CI: core-agent-security.
- **Chronione testy akceptacyjne** wymusza konfiguracja, nie prompt. CODEOWNERS tylko wskazuje recenzentów; wiąże dopiero
  z ochroną gałęzi „Require review from Code Owners” i wymaganym checkiem. Zmiany scenariuszy idą w osobnym PR niż kod —
  check w CI odrzuca PR zmieniający oba naraz. Pilnuj też definicji kroków i adapterów: tam da się „zazielenić” scenariusz.
Szczegóły: `references/agent-prs.md`.

## Przegląd, także przez AI
- Pierwszy przegląd może zrobić agent; rozstrzygający robi człowiek i patrzy na zachowanie i ryzyko, nie na styl.
- Rozdział obowiązków: agent nigdy nie zatwierdza własnego kodu. Ochrona gałęzi wymaga zatwierdzenia przez człowieka
  i zielonego CI; agent może pushować poprawki na gałąź PR; scala człowiek.
- Zasady są w `REVIEW.md` w katalogu głównym (nie w CLAUDE.md): szablon `references/review-md.md`. Szkic z rekonstrukcji
  kodu staje się `REVIEW.md` poleceniem `ai_review.py review-md` po zatwierdzeniu przez człowieka.
- Narzędzia: usługa Code Review w Claude Code albo `anthropics/claude-code-action@v1` (odpowiada na `@claude` albo wykonuje
  `prompt`), instalowana przez `/install-github-app`. Aplikację instaluje i sekrety ustawia człowiek.
- **Gotowy workflow fabryki:**
  1. `python3 .claude/skills/core-git-workflow/scripts/ai_review.py install` (`--all-prs` — przegląd każdego PR, nie tylko
     z etykietą `ai-review`) zapisuje `.github/workflows/ai-review.yml`; bez `--force` nie nadpisuje.
  2. Dodaj sekret repozytorium `ANTHROPIC_API_KEY`.
  3. W ochronie gałęzi wymagaj statusu `ai-review/verdict`.
  4. `REJECTED` albo brak/niepoprawny wynik → czerwony status; człowiek może obejść etykietą `ai-review-override`.
  PR-y z forków są pomijane (bez sekretów). Jak działa bramka i co ją psuje: `references/ai-review-in-ci.md`.
- Strój co miesiąc: sprawdź, ile uwag było trafnych, ogranicz drobiazgi, wyłącz pliki generowane i sprawdzane przez CI.
  Zmiany wrażliwe (auth, IaC, CI) → `security-reviewer` przed scaleniem. Przegląd względem planu z człowiekiem → qa-change-review.

## Scalanie, stosy, konflikty
- Jedna strategia na repozytorium, wymuszona w ustawieniach: squash (małe PR, czysta historia), rebase (liniowa historia
  z każdym commitem), merge commit (gdy liczy się zapis scalenia, np. gałęzie wydań). Przy squashu ustaw tytuł sam:
  `gh pr merge 42 --squash --subject "feat(export): CSV export (#42)"`. Scalaj tylko przy zielonym CI i wymaganych zatwierdzeniach.
- Po squashu podstawy stosu następny PR wciąż niesie stare commity:
  `git fetch origin main` → `git rebase --onto origin/main <stara-gałąź-bazowa> <gałąź>` →
  `git push --force-with-lease` (własna gałąź, po zgodzie) → `gh pr edit <N> --base main` → poczekaj na CI → scal.
- Konflikty: zrozum obie strony, nigdy nie bierz hurtem „swojej”, potem uruchom testy. W trakcie rebase zatrzymaj się i pokaż
  człowiekowi pliki; dalej `git add` + `git rebase --continue` albo `git rebase --abort`.
Szczegóły: `references/merging-and-pr-stacks.md`.

## Przykład
Prośba: „Wypchnij eksport CSV, jakkolwiek.” Gałąź `story/tsk-57-csv-export`, faza 2 z 3 gotowa. `git status` pokazuje
`src/export/csv.py`, `tests/export/test_csv.py`, raport kroku `012-csv-export.md` i niezwiązany `config/local.yaml`.
Agent dodaje trzy pierwsze po ścieżce, pyta o `config/local.yaml` (odpowiedź: zostaw), sprawdza `git diff --staged`,
commituje `feat(TSK-57): endpoint and serializer (f2)` ze `Change: TSK-57`. Hook pre-commit pada na błędzie lintu →
poprawka, nowy commit `d4e81a2`, SHA dopisane do Postępu. Zdalne repo odrzuca push, bo agent zrobił rebase na `origin/main`:
pyta, potem `git push --force-with-lease origin story/tsk-57-csv-export` — nigdy `--force` i nigdy na `main`.
