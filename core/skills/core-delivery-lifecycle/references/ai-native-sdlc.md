When agents write code faster than people can review, test, deploy and maintain it, the bottleneck moves to those
stages. Controls that were built for human pace (a reviewer reads every line, a tester runs every case) are rebuilt as
artifacts, hooks, rules and agent review layers, while a human stays on critical and regulated code and on every
approval that matters.

## 1. The principle
- Every stage ends with an artifact in the repository that the next stage reads; the commit sequence is the audit
  trail.
- The agent does the work; checks run automatically; the human decides at gates.
- A mistake an agent makes for the second time becomes a rule in `CLAUDE.md` (with the human's consent) or a hook.

## 2. The artifact chain
intent (brief) → spec (requirements) → plan → diff + tests → PR + review → maintenance record → new brief.

Where the source of truth lives — choose one per project and write it down:
| Option | When | Cost |
|---|---|---|
| Repository files (`docs/project/…`) | agents do most of the work; review happens in PRs | people outside engineering need repo access or exports |
| External tool (tracker, wiki) read through a connector | the organisation already runs on it | agents depend on the connector; mirror the IDs in commits |
| Both, with minimal cross-links | transition period | links rot; one side must be declared authoritative |

## 3. Plan before code, self-verification, red tests
- Nothing is implemented without an accepted plan (`05-plan/plan.md`, or the **Step plan** of the step report).
  When the work deviates, the plan is updated **in the same commit** as the code.
- The agent verifies itself with **one command** (tests + lint + type check, or a project script) and shows the output.
- A bug fix starts from a regression test that fails, and the test is not weakened to make it pass. The `tdd_guard`
  hook enforces this: rule A — the first production edit needs a test edit followed by a red run; rule B — after a
  number of production edits without a new test, the next behaviour needs a new test; rule C — weakening a test
  (fewer assertions, added skips) triggers `CLAUDE_TDD_WEAKEN=warn|ask|deny|off` (default warn).

## 4. Refinement with agents
- Before implementing, the executor (agent or person) **retells in its own words** the problem, the expected behaviour,
  the intended approach and the risks. A mismatch found here costs minutes; found in review, it costs a rewrite.
- The issue is **written by a human for a human**: the goal, the context, what done looks like. A description
  generated by AI and implemented by AI without anyone restating it has no point where understanding is checked.
- Deeper review (design review, second reviewer) only above a size or risk threshold the team sets — not on every
  change. Specific thresholds in blog articles are practitioner opinion; calibrate on your own data.

## 5. Evaluations of agent configuration
The agent's configuration — `CLAUDE.md`, skills, hooks, prompts, the review prompt, the model version — is code and gets
regression tests.
- **Case set:** start with a few dozen real tasks from the project (Anthropic's guidance suggests roughly 20–50
  [unverified: exact figure]), each with the expected behaviour. Every incident and every escaped defect caused by an
  agent adds a case.
- **For a reviewer or checker agent:** label the cases — diffs with a planted defect (it must be found) and clean diffs
  (it must stay silent, measuring false alarms).
- **Three kinds of check:** structural (the output parses, has the required fields and verdict line), model-graded
  (a judge model scores against a rubric), programmatic (a script compares the result with the expected one).
- **When to run:** on every change of configuration or model, and before rolling a new configuration out to the team.
  Decide in advance what counts as a red run (e.g. any regression on a previously passing planted-defect case).
- Any evaluation runner will do (an open-source eval harness, the factory's `skill_gate.py` for skills, a script in CI);
  record results and cost with the change.

## 6. AI review of pull requests
- The review follows `REVIEW.md` in the repository root: separate passes for bugs and logic, security, and agreement
  with the spec and plan; findings with a severity; tuned monthly (where did it miss, where was it noise).
- A human approves the merge (branch protection); hooks act as approval gates for protected actions.
- An agent in CI runs sandboxed with least-privilege, short-lived credentials; secrets never enter its context.
- Setup in CI: `.claude/skills/core-git-workflow/references/ai-review-in-ci.md`; fresh-context review locally:
  `/code-review`, the security-reviewer agent.

## 7. Control bands and graded reactions
Production and process metrics (5xx rate, latency, PR cycle time, change failure rate) are watched with control bands
instead of fixed thresholds, so normal noise does not page anyone.

```
python3 .claude/skills/core-delivery-lifecycle/scripts/control_band.py metric.csv --baseline 30 --side upper
```
The first N points set the mean and standard deviation; `--side upper` counts only increases (errors), `lower` only
decreases (success rates). Western Electric rules map to reactions:
| Rule | Level | What the agent may do |
|---|---|---|
| one point beyond 3σ | act | open a PR or run an already approved runbook |
| 2 of 3 consecutive beyond 2σ, same side | diagnose | read-only investigation, write a change brief with evidence |
| 4 of 5 beyond 1σ, same side | log | record only |
| 8 in a row on one side of the mean | log | record only |
Exit code 2 means bad data (e.g. a flat baseline). Nothing reaches production without the human's approval; a
diagnosis ends with a change brief, not a hot fix.

## 8. Measures
Per stage, pair a leading measure (early signal) with a lagging one (result):
| Stage | Leading | Lagging |
|---|---|---|
| Intent and spec | open questions closed before B2 | requirement changes after B2 |
| Plan | share of items with a requirement ID and verification | plan deviations per step |
| Build | time to first review, PR size | rework after review |
| Review and test | review findings per PR, false-alarm rate | escaped defects |
| Deploy | deployment frequency, lead time for changes | change failure rate, time to restore (DORA; eng-continuous-delivery) |
| Maintain | open issues by severity, patch age | incidents, cost per change |

- Flow measures: PR size, time to first review, open PRs per person.
- **Autonomy and activity measures** (share of PRs written by agents, review hours, task duration) are reported only
  **next to outcome measures** — escaped defects, change failure rate, cost per change, time from intent to production,
  the business metric. Alone, an activity measure becomes a target and stops measuring anything (Goodhart's law).
- Take numbers from the source systems (VCS, CI, tracker, monitoring), not from agent self-reports.

## 9. Artifact budget in a PR
Plans and reports must help the review, not drown it.
```
python3 .claude/skills/core-delivery-lifecycle/scripts/pr_budget.py --base main [--json]
```
Counts lines added under `docs/project/**`, `docs/test/**`, `docs/work/**`, `.tf/**`, `**/evidence/**` (plus patterns
from `.claude/pr-budget.json`) against code. Over budget: artifacts above 50% of added lines in a PR that also changes
code, one artifact above 600 lines, a plan above 300. First line `Werdykt: OK | OVER`, exit 1 when over. Keep what the
review needs; move raw logs and evidence out of the PR.

## 10. Governance and settings
Organisation-wide controls belong in managed settings: permission denials, an enforced sandbox, approvals for protected
actions that only hooks can grant, allowlists of MCP servers and plugins, minimum model versions. Key names change
between releases — check them in the current Claude Code settings documentation, do not guess.

## 11. Adoption levels
Introduce the loop in steps, each proven before the next: (1) agents in individual sessions with a plan and one
verification command; (2) artifacts in the repo and fresh-context review; (3) AI PR review with `REVIEW.md` and human
merge; (4) evaluations of configuration in CI; (5) control bands with graded reactions; (6) managed settings across the
organisation. [Own grouping; the playbook's own list of practices is longer.]

## 12. Vocabulary (AI-DLC)
AWS's AI-Driven Development Life Cycle names three phases — **inception** (intent to units of work), **construction**
(design and code), **operations** — and short, intense cycles called **bolts** instead of sprints. **Mob elaboration**
and **mob construction** are sessions where the team validates, together and in real time, what the AI proposes. A
**unit of work** is a cohesive piece that can be built and deployed independently (close to a vertical slice).

## 13. Anti-patterns
- Stages that leave no artifact — the next session guesses.
- Weak verification ("looks fine") instead of a command with output.
- Evaluations not updated after incidents or model changes.
- Approvals without a gate (the agent merges or deploys).
- Secrets in the agent's context or logs.
- An AI reviewer nobody tunes — the team learns to ignore it.
- Activity measures reported as success.
